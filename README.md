# Авито.Кухня — MVP

Сервис связывает web-клиент доставки с заведениями. В репозитории есть сам
`Kitchen Core`, PostgreSQL и отдельный, запускаемый вместе с ним пример сервиса
заведения — «Пиццерия Марио».

## Что реализовано

| Область | Решение |
| --- | --- |
| API для web-клиента | список открытых заведений, меню, создание/отмена заказа, история заказов и polling статуса |
| API для заведений | идемпотентное подключение заведения, синхронизация меню, управление доступностью, очередь заказов и смена статусов |
| Интеграция | Core отправляет webhook о новом заказе; сервис заведения через собственный API принимает/отклоняет заказ и обновляет статусы |
| Данные | PostgreSQL, Alembic-миграция, снимки цен, адрес доставки, история статусов, внешние идентификаторы партнёра |
| Документация | OpenAPI, схема БД, C4 Level 2, два CJM в PlantUML |
| Качество | конфигурация Ruff, тесты API-контракта и конечного автомата статусов |

## Быстрый запуск

Нужен Docker Desktop. Из корня репозитория:

```bash
docker compose up --build
```

После старта:

- Core и Swagger UI: <http://localhost:8000/docs>
- OpenAPI Core: <http://localhost:8000/openapi.json>
- пример сервиса заведения: <http://localhost:8001/health>

Сервис заведения при старте безопасно повторяет синхронизацию: создаёт или
обновляет «Пиццерию Марио» и три позиции меню. У «Колы 0.5» остаток `0` — это
готовый сценарий проверки отсутствия товара.

## Демонстрация полного сценария

1. В Swagger откройте `GET /client/establishments` и скопируйте `id` заведения.
2. В `GET /client/establishments/{establishment_id}/menu` получите `id` пиццы.
3. Создайте заказ через `POST /client/orders`, подставив свои UUID и адрес:

```json
{
  "user_id": "00000000-0000-4000-8000-000000000001",
  "establishment_id": "<id-заведения>",
  "delivery_address": "Москва, ул. Тестовая, 1",
  "comment": "Домофон 12",
  "items": [{"product_id": "<id-пиццы>", "quantity": 1}]
}
```

4. Core отправит уведомление. Убедитесь, что заказ появился в
   `GET http://localhost:8001/orders`.
5. Примите его через API примера заведения:

```bash
curl -X POST http://localhost:8001/orders/<order_id>/decision \
  -H "Content-Type: application/json" -d '{"accept":true}'
```

6. Последовательно передайте `preparing`, `ready`, `completed` через
   `POST http://localhost:8001/orders/<order_id>/status`. Клиент видит
   результат и журнал переходов в `GET /client/orders/{order_id}`.

Для ветки отказа передайте `{"accept": false, "reason": "нет свободных курьеров"}`.
Для сценария отсутствия товара попробуйте заказать «Колу 0.5»: Core вернёт `409`
до создания заказа.

## Архитектура и данные

- `kitchen-core/` — FastAPI и PostgreSQL. Это источник истины по каталогу,
  остаткам и заказам.
- `establishment-service/` — отдельный Flask-сервис-партнёр. Он принимает
  webhook и предоставляет небольшой API оператору заведения.
- `docs/` — [C4](docs/c4_container.puml), [CJM пользователя](docs/cjm_user.puml),
  [CJM заведения](docs/cjm_establishment.puml), [схема БД](docs/db_schema.md) и
  [OpenAPI](docs/openapi.yaml).

`.puml`-диаграммы можно просмотреть через расширение PlantUML в VS Code
(Alt+D для превью) или вставив содержимое файла на
<https://www.plantuml.com/plantuml/uml/>.

Заказ принадлежит ровно одному заведению. `user_id` — идентификатор из
внешнего сервиса аккаунтов; отдельную таблицу пользователей не создаём, потому
что авторизация и аутентификация прямо исключены из задания. У заведения есть
стабильный `partner_id`, а у позиции меню — опциональный `external_id` из POS:
это делает повторную синхронизацию меню идемпотентной.

При создании заказа Core блокирует в PostgreSQL строки выбранных товаров через
`SELECT ... FOR UPDATE`, проверяет остатки и резервирует их в одной транзакции.
Если заведение отклонило заказ или пользователь отменил его до принятия, остаток
возвращается. Цена и общая стоимость фиксируются в заказе как `Decimal(10,2)`.

## Проверки качества

Локально, с Python 3.12+:

```bash
cd kitchen-core
python -m pip install -e ".[dev]"
ruff check app tests
pytest
```

Ruff также настроен для `establishment-service` в его `pyproject.toml`.

## Ограничения MVP

- Нет аутентификации. В production клиентский `user_id` берётся из access token.
  `partner_api_key` сохраняется в хешированном виде при регистрации заведения
  (`PUT /establishments/{partner_id}`), но сверка ключа на последующих
  partner-запросах (decision, status, product upsert) не реализована в рамках
  MVP. В production нужна зависимость FastAPI, которая проверяет заголовок
  вида `X-Partner-Api-Key` против сохранённого хеша для соответствующего
  `establishment_id`, и аналогичная проверка `KITCHEN_ADMIN_API_KEY` для
  самого эндпоинта регистрации.
- Webhook доставляется best-effort. При недоступном партнёре заказ не теряется,
  но для гарантированной доставки в production нужен transactional outbox,
  очередь и повторы; партнёр также может забирать очередь через свой Core API.
- Нет платёжного и курьерского доменов, расчёта ETA, промокодов и мультизаказов.
- Reference-сервис заведения хранит входящие webhook'и в памяти: он
  демонстрирует контракт, а не заменяет POS. При перезапуске партнёр восстанавливает
  работу pull-запросом к `GET /establishments/{id}/orders`.

План использования AI и принятые человеком архитектурные решения находятся в
[docs/development-plan.md](docs/development-plan.md).
